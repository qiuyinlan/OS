# 第12章 进一步完善内核

本章主要实现[[系统调用]]机制，并完善`printf`函数和堆内存管理。

## 12.1 Linux 系统调用浅析
- **概念**: [[系统调用]]是[[用户进程]]请求[[操作系统]]服务的一种机制。
- **用户态接口**:
    - `syscall()`函数: [[glibc]]提供的库函数，统一接口，参数通过寄存器传递。
    - `_syscallX`宏: 较旧的方式，针对不同参数个数有不同宏，参数通过寄存器传递。
- **内核入口**: Linux 使用 `int 0x80` 作为[[系统调用]]的统一入口。
- **参数传递**: 通常通过[[寄存器]]传递参数（`eax`传递[[系统调用号]]，`ebx`, `ecx`, `edx`, `esi`, `edi`等传递参数），高效避免了用户栈和内核栈之间的多次内存访问。

## 12.2 系统调用的实现

### 12.2.1-12.2.4 框架与入口
- **框架**:
    1.  用[[中断门]]实现，效仿Linux使用`0x80`号中断作为[[系统调用]]入口。
    2.  在[[中断描述符表 (IDT)]]中安装`0x80`号中断对应的[[门描述符]]，其DPL设置为3（允许用户态调用）。
    3.  建立[[系统调用子功能表 (syscall_table)]]，利用`eax`寄存器中的[[系统调用号]]索引对应的处理函数。
    4.  用宏实现用户空间的[[系统调用接口 (_syscallX)]]，最大支持3个参数。
- **`syscall_handler`**: `0x80`号中断对应的中断处理例程，汇编实现。
    -   保存上下文。
    -   从用户栈或寄存器中获取[[系统调用号]]及参数。
    -   调用`syscall_table[eax * 4]`中的处理函数。
    -   将返回值存入栈中`eax`的位置。
    -   `jmp intr_exit`，返回用户态。

### 12.2.5-12.2.7 实现 `sys_getpid`
- **`syscall_table`**: 函数指针数组，存储所有[[系统调用]]处理函数的地址。
- **`sys_getpid()`**: 返回当前任务的`pid`。
- **`pid`管理**:
    -   在`task_struct`中增加`pid`成员。
    -   实现`allocate_pid()`和`release_pid()`，通过[[位图]]管理`pid`的分配与释放，并使用[[锁]]保证唯一性。
    -   `thread_init()`中初始化`pid`池，`init_thread()`中为每个线程分配`pid`。
- **`getpid()`用户接口**: 用户态通过宏`_syscall0(SYS_GETPID)`调用。

## 12.3 让用户进程“说话”：实现 `printf`

### 12.3.1 可变参数的原理
- **`printf`函数**: 支持可变参数。
- **`va_list`, `va_start`, `va_arg`, `va_end`**: [[GCC]]提供的宏，用于处理可变参数。
    - `va_list`: 指针类型，用于指向可变参数在栈中的地址。
    - `va_start(ap, v)`: 初始化`ap`，使其指向第一个可变参数。
    - `va_arg(ap, type)`: 使`ap`指向下一个参数并返回当前参数的值。
    - `va_end(ap)`: 清空`ap`。
- **参数传递**: C语言采用调用者把参数从右向左压入栈中，并由调用者清理栈的方式。

### 12.3.2-12.3.4 实现 `write` 和 `printf`
- **`sys_write(fd, buf, count)`**: [[write系统调用]]的内核实现。
    -   当`fd`为`stdout_no`时，直接通过`console_put_str`输出。
    -   当`fd`为文件描述符时，调用`file_write`将`buf`数据写入文件。
- **`vsprintf(str, format, ap)`**: 格式化输出函数，将`ap`指向的可变参数按`format`格式输出到`str`字符串中。
    -   包含`itoa`函数用于将整数转换为字符串。
    -   支持`%x` (十六进制)、`%c` (字符)、`%s` (字符串)、`%d` (十进制整数)等格式符。
- **`printf(format, ...)`**: `vsprintf`和`sys_write`的封装。

## 12.4 完善堆内存管理
之前实现的内存管理过于粗糙（仅以4KB页框为单位），无法满足小内存块（几十、几百字节）的分配需求。

### 12.4.1 `malloc`底层原理
- **`arena` (内存舞台)**:
    -   一个`arena`是内存管理的基本单元，通常占用1个或多个页框。
    -   分为两部分:
        1.  **元信息**: `arena`结构体本身，记录`arena`的状态和[[内存块描述符 (mem_block_desc)]]指针。
        2.  **内存池区域**: 实际用于划分成小内存块的区域。
    -   **小内存块 (`mem_block`)**: `arena`内部会被平均拆分成多个相同规格的小内存块。规格有多种（16, 32, 64, 128, 256, 512, 1024字节）。
- **`mem_block_desc` (内存块描述符)**:
    -   每种规格的内存块有一个对应的`mem_block_desc`。
    -   记录该规格的`block_size`，以及一个空闲内存块链表(`free_list`)。
    -   **汇聚同规格内存块**: 负责汇集所有`arena`中相同规格的空闲内存块。
- **大内存分配**: 如果申请内存大于1024字节，`sys_malloc`会直接分配整页框（不再拆分），此时`arena`的`desc`为`NULL`。

### 12.4.2 底层初始化
- **数据结构**: `struct mem_block`, `struct mem_block_desc`, `struct arena`。
- **初始化**: `block_desc_init()`函数初始化`7`种规格的内核内存块描述符数组（`k_block_descs`）。

### 12.4.3 实现 `sys_malloc`
- **`sys_malloc(size)`**: 分配`size`字节的内存。
- **分配策略**:
    1.  判断调用者是[[内核级线程]]还是[[用户进程]]，选择对应的内存池和[[内存块描述符 (mem_block_desc)]]数组。
    2.  如果`size > 1024`字节，则按页框分配大内存。分配的`arena`的`desc`为`NULL`，`large`为`true`。
    3.  如果`size <= 1024`字节，遍历[[内存块描述符 (mem_block_desc)]]数组，找到最合适的内存块规格。
    4.  如果对应规格的`mem_block_desc->free_list`为空，则`malloc_page(PF, 1)`分配新的页框创建`arena`。
    5.  将新的`arena`拆分成`mem_block`并加入`mem_block_desc->free_list`。
    6.  从`mem_block_desc->free_list`中弹出一个`mem_block`，返回其地址。

### 12.4.4 内存的释放
- **`pfree(pg_phy_addr)`**: 回收物理页框，在物理内存池[[位图]]中清零对应位。
- **`page_table_pte_remove(vaddr)`**: 将页表中`vaddr`对应的`PTE`的`P`位清零，并刷新TLB。
- **`vaddr_remove(pf, _vaddr, pg_cnt)`**: 在虚拟地址池[[位图]]中清零对应位。
- **`mfree_page(pf, _vaddr, pg_cnt)`**: 封装上述三个功能，释放页框级别的内存。

### 12.4.5 实现 `sys_free`
- **`sys_free(ptr)`**: 内存释放的统一接口，支持任意大小内存。
- **释放策略**:
    1.  根据`ptr`所在的`arena`判断是大内存还是小内存块。
    2.  **大内存**: 如果`arena->desc`为`NULL`且`arena->large`为`true`，说明是整页框分配，直接调用`mfree_page`释放整个`arena`。
    3.  **小内存块**: 将`mem_block`回收（`list_append`）到`arena->desc->free_list`。
    4.  检查`arena`中的所有`mem_block`是否都已空闲。如果是，则释放整个`arena`（调用`mfree_page`）。
