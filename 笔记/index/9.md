"不管理" ≠ "不分池"

  "不管理"的意思是：这部分内存不纳入内存池的管理范围，不能用 
  get_kernel_pages() 分配。

  让我画图说明：

  物理内存全景（32MB为例）：
  ┌────────────────────────────────────────┐
  │ 0x0000000 ~ 0x00fffff (1MB)            │
  │ 【已被占用，不能再分配】               │
  │ - BIOS数据                             │
  │ - 中断向量表                           │
  │ - MBR代码（0x7c00处）                  │
  │ - Loader代码（0x900处）                │
  │ - 内核代码（加载到这里）               │
  │ - 内核栈、全局变量等                   │
  │                                        │
  │ 状态：已经在使用中，不能动！           │
  ├────────────────────────────────────────┤
  │ 0x100000 ~ 0x1fffff (1MB)              │
  │ 【页目录表和页表，不能再分配】         │
  │ - 页目录表（1个，4KB）                 │
  │ - 页表（255个，每个4KB）               │
  │                                        │
  │ 状态：分页机制需要，不能动！           │
  ├────────────────────────────────────────┤
  │ 0x200000 ~ 0xffffff (14MB)             │
  │ 【内核物理内存池 - 可以分配】         │
  │                                        │
  │ 用位图管理这部分内存                   │
  │ kernel_pool 负责                       │
  ├────────────────────────────────────────┤
  │ 0x1000000 ~ 0x1dfffff (14MB)           │
  │ 【用户物理内存池 - 可以分配】         │
  │                                        │
  │ 用位图管理这部分内存                   │
  │ user_pool 负责                         │
  └────────────────────────────────────────┘

  总结"不管理"：
  - ✅ 这些内存确实在使用（被内核代码、页表占用）
  - ❌ 但不用位图管理，不能动态分配
  - ❌ 不属于任何内存池

  疑问2：为什么分两个池就能保证内核永远有内存？

  这是个隔离保护的设计！让我用具体场景解释。

  场景1：如果只有一个内存池（不好的设计）

  只有一个大内存池（28MB）：
  ┌────────────────────────────────────────┐
  │         统一内存池（28MB）              │
  │  内核和用户程序都从这里申请            │
  └────────────────────────────────────────┘

  发生的问题：
  时刻1：内核申请了5MB
  时刻2：用户程序A申请了10MB
  时刻3：用户程序B申请了13MB
  时刻4：内核想申请内存 → ❌ 失败！只剩0MB
          ↓
      系统崩溃！😱

  问题：
  - 用户程序可能（恶意或无意）耗尽所有内存
  - 内核无法再分配内存
  - 无法创建新进程、无法分配PCB
  - 系统死机！

  场景2：分成两个池（好的设计）

  分成两个独立的池：
  ┌────────────────────────────────────────┐
  │    内核物理内存池（14MB）               │
  │    只有内核能用                         │
  └────────────────────────────────────────┘
  ┌────────────────────────────────────────┐
  │    用户物理内存池（14MB）               │
  │    只有用户程序能用                     │
  └────────────────────────────────────────┘

  发生的情况：
  时刻1：内核从内核池申请5MB  → 内核池剩余9MB
  时刻2：用户A从用户池申请10MB → 用户池剩余4MB
  时刻3：用户B从用户池申请4MB  → 用户池剩余0MB ⚠️
  时刻4：用户C想申请内存       → ❌ 用户池没内存了
          ↓
      用户C被拒绝（返回NULL）
      但内核池还有9MB！✅
          ↓
  时刻5：内核想申请内存        → ✅ 成功！内核池还有9MB
          ↓
      系统继续运行！内核可以：
      - 杀死占用内存过多的进程
      - 分配资源给新进程
      - 正常管理系统

  优势：
  - ✅ 用户程序耗尽用户池 → 只是用户程序失败
  - ✅ 内核池完全独立 → 内核永远有内存可用
  - ✅ 内核可以回收用户内存 → 杀死恶意进程
  - ✅ 系统永远可控

  ---
  代码层面的保护

  看看代码是如何实现隔离的：
```c

  // kernel/memory.c

  // 两个全局变量，完全独立
  struct pool kernel_pool;  // 内核专用
  struct pool user_pool;    // 用户专用

  // 分配内存时，必须指定从哪个池分配
  void* malloc_page(enum pool_flags pf, uint32_t pg_cnt) {
      // 根据标志选择池
      struct pool* mem_pool = (pf & PF_KERNEL) ? &kernel_pool : &user_pool;

      // 只从选定的池中分配
      void* page_phyaddr = palloc(mem_pool);

      // ...
  }

  // 内核分配：强制使用内核池
  void* get_kernel_pages(uint32_t pg_cnt) {
      return malloc_page(PF_KERNEL, pg_cnt);  // 只能用内核池
  }

  // 用户分配：强制使用用户池（将来实现）
  void* get_user_pages(uint32_t pg_cnt) {
      return malloc_page(PF_USER, pg_cnt);    // 只能用用户池
  }

```
  关键：
  - 内核调用 get_kernel_pages() → 只从 kernel_pool 分配
  - 用户调用 get_user_pages() → 只从 user_pool 分配
  - 两个池互不干扰！
